### Common requirements

- Keep capability descriptors and request/result semantics provider-neutral and separate from workflow intent.
- Separate capability discovery, hardware/resource-aware routing, policy and authorization, provider adapters, and runtime execution.
- Represent unsupported or partially supported capabilities explicitly; do not silently degrade streaming, modalities, cancellation, locality, or resource constraints.
- Define lifecycle, streaming, cancellation, timeout, retry, partial-result, error, and observability semantics before public contracts.
- Treat locality and remote execution authorization as explicit policy, not an automatic fallback.
- Require versioning, conformance tests, reproducible benchmarks, and Project Owner approval before stabilizing a public provider contract.

### Architectural risks and trade-offs

- A narrow common interface may erase image, streaming, session, memory, or runtime-specific semantics; a richer interface increases compatibility surface and premature-abstraction risk.
- Hardware-aware discovery improves feasibility but must remain routing evidence rather than workflow schema.
- Provider-specific options can preserve capability but become accidental public coupling.
- Runtime differences make cancellation, retry safety, partial output, resource estimates, and lifecycle guarantees uncertain.
- Remote execution can change data placement, privacy, credentials, latency, and auditability.
- “Image inference” is underspecified; image understanding, generation, transformation, and embeddings require different schemas and benchmarks.

No material contradiction appeared between reports. The main unresolved trade-off is how much capability/routing separation to introduce while keeping the first approved boundary narrow and validated by representative use cases.

### Open questions

- Which capability families and image modalities are in the first approved scope?
- Which descriptor fields and stream events are stable public data versus provider extensions?
- What locality, remote-authorization, resource-estimate, cancellation, retry, and failure guarantees are required?
- How are model identity, revisions, artifacts, licenses, and descriptor freshness represented?
- What provider conformance matrix and benchmark protocol qualify support?

### Proposed next steps

1. Define representative use cases and a verified capability matrix for the three runtime classes.
2. Draft a proposal RFC for capability requests, descriptors, negotiation, route plans, typed results/events, errors, cancellation, locality, and compatibility.
3. Define provider conformance, security, reliability, and performance acceptance tests.
4. Obtain Project Owner approval before implementing or publishing any provider interface.
